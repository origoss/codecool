DaemonSets: one Pod on every node

Your win: you can explain why the CNI, the Pod Identity Agent and log collectors run as DaemonSets, predict on which nodes a DaemonSet puts its Pods, and roll out a new version node by node.

Before this: lesson 00 (labels and selectors), and you have already met three DaemonSets without the name: aws-node (the VPC CNI that enforces NetworkPolicy in lesson 04), eks-pod-identity-agent (which hands AWS credentials to ESO in lesson 03) and kube-proxy. Example files: examples/daemonsets/.

What a DaemonSet is for

"A DaemonSet ensures that all (or some) Nodes run a copy of a Pod. As nodes are added to the cluster, Pods are added to them. As nodes are removed from the cluster, those Pods are garbage collected."[1] Typical uses: a storage daemon, a log collector or a monitoring agent on every node.[1] Network plugins "often include a component that runs as a DaemonSet", which makes sure the node it runs on "has working cluster networking".[1]

Which nodes? Taints, tolerations and selectors

Without extra settings a DaemonSet puts a Pod on all nodes. You narrow it with nodeSelector or node affinity in the Pod template.[3] In the other direction, a node can push Pods away with a taint; only Pods with a matching toleration may land there.

Because node agents must run even on sick nodes, the DaemonSet controller adds a set of tolerations to its Pods automatically: for not-ready, unreachable, disk-pressure, memory-pressure, pid-pressure and unschedulable nodes.[4] Why: otherwise "you could end up in a deadlock situation where the node is not marked as ready because the network plugin is not running there, and at the same time the network plugin is not running on that node because the node is not yet ready."[4]

The automatic list does not include any other taint. On a self-managed cluster (kubeadm, kind) the control-plane nodes carry node-role.kubernetes.io/control-plane:NoSchedule, so you add that toleration yourself if the agent must run there too. On EKS you never see the control-plane nodes: AWS runs them, so DaemonSets cover your worker nodes only. The demo therefore uses a taint of our own. Dedicated node groups on EKS are tainted the same way (the taints setting of a managed node group).

Updating: node by node

A DaemonSet has two update strategies. RollingUpdate, the default, replaces old Pods automatically "in a controlled fashion"; OnDelete creates the new Pod on a node only after you delete the old one by hand.[5] maxUnavailable (default 1) sets how many nodes may be without a ready Pod during the update; maxSurge (default 0) lets the new Pod start before the old one stops.[5] Changing node labels also changes the Pods: the DaemonSet "will promptly add Pods to newly matching nodes and delete Pods from newly not-matching nodes."[6]

One Pod per node

  1. 01-node-agent.yaml: a tiny agent that prints the name of its node, read with the Downward API (fieldPath: spec.nodeName).

    apiVersion: apps/v1
kind: DaemonSet                 # no replicas field: the nodes decide
metadata:
  name: node-agent
  namespace: demo
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: node-agent
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
  template:
    metadata:
      labels:
        app.kubernetes.io/name: node-agent
    spec:
      containers:
      - name: agent
        image: busybox:1.37
        command: ["sh", "-c", "while true; do echo \"agent v1 on node $NODE_NAME\"; sleep 30; done"]
        env:
        - name: NODE_NAME
          valueFrom:
            fieldRef:
              fieldPath: spec.nodeName
        resources:
          requests: {cpu: 10m, memory: 16Mi}
          limits: {memory: 32Mi}
    kubectl apply -f examples/daemonsets/00-namespace.yaml -f examples/daemonsets/01-node-agent.yaml
kubectl get daemonset node-agent -n demo
kubectl get pods -n demo -o wide

Best practices

  • Set resource requests and limits. A DaemonSet runs on every node, so its footprint is multiplied by the node count and taken from every node's capacity.
  • Give critical agents a high priority. If the Pod "cannot fit on the node, the default scheduler may preempt (evict) some of the existing Pods based on the priority of the new Pod"; the docs recommend a higher priorityClassName when it must run on each node.[7] Kubernetes ships system-node-critical and system-cluster-critical for this.[8]
  • Treat node agents as high-risk. Many need hostNetwork or hostPath volumes to do their job, and both are forbidden by the Baseline Pod Security Standard for normal workloads.[9] A compromised agent sits on every node. Use trusted images, a dedicated ServiceAccount with least-privilege RBAC (lesson 02), and keep them in their own namespace.
  • Keep the default RollingUpdate with maxUnavailable: 1 unless you have a reason; use OnDelete only when you must control exactly when each node switches.[5]
  • Prefer a DaemonSet to bare Pods or scripts on the node. It replaces Pods lost to node failure or maintenance, and you manage daemons with the same tools, logs and limits as apps.[10]
