AWS Secrets Manager and the External Secrets Operator

Your win: you can draw the path a password takes from AWS Secrets Manager, through the External Secrets Operator, into a Kubernetes Secret and finally into a Pod. You can say which object does what (SecretStore, ExternalSecret, target Secret), why the operator logs in to AWS with EKS Pod Identity instead of IRSA or access keys, and where to look first when kubectl get externalsecret says SecretSyncedError.

The example files are in examples/external-secrets-aws/.

Why the password must not live in Git

In lesson 01 you wrote a Secret manifest. Its data is only base64: anyone who can read the file can decode it. If that file is committed, the password is now in every clone, every fork and every CI cache. GitHub's own advice for a leaked credential is to rotate it first, because rewriting history cannot reach other people's clones and forks.[1] And inside the cluster, Secrets are stored unencrypted in etcd by default; anyone who may create a Pod in a namespace can read every Secret in it.[2]

So production teams split the job: Git holds the reference to a secret (its name, which keys you want), a dedicated secret store holds the value, and a controller copies the value into the cluster when it is needed.

Industry practice. Never commit real secret values, not even "just for dev". Keep the values in a managed store with access control and an audit log, and give Kubernetes only the pointer. Sealed Secrets, SOPS and HashiCorp Vault solve the same problem in other ways; they are out of scope today.

AWS Secrets Manager in one minute

A secret in AWS Secrets Manager is a named, encrypted value of up to 64 KB. The usual shape is a small JSON object of key/value pairs, such as {"username": "app", "password": "…"}.[3] What you get on top of a plain file:

FeatureWhat it means for you
Encryption with KMSThe value is encrypted at rest; the default key aws/secretsmanager costs nothing extra.
IAM access controlWho may read which secret is an IAM policy, down to a name prefix like codecool/*.
VersionsEvery put-secret-value makes a new version; the current one carries the label AWSCURRENT.
AuditEvery create and read is logged in CloudTrail.
Price$0.40 per secret per month plus $0.05 per 10,000 API calls.[4]

Each secret's ARN ends in a random six-character suffix, for example …:secret:codecool/demo/app-db-a1b2c3. That is why IAM policies always end the name with *.

External Secrets Operator: one controller, three objects

The External Secrets Operator (ESO) is a controller you install with Helm. It reads ExternalSecret objects, fetches the values they name from an external API, and writes them into ordinary Kubernetes Secrets, which it then keeps in sync.[5] Your Pods do not know ESO exists: they read a normal Secret, exactly as in lesson 01.

                                                                         │  Pod app  │
                                                                         └───────────┘
ObjectAnswersScope
SecretStoreHow to reach the provider: which service, region, credentials.One namespace. Only ExternalSecrets in the same namespace may use it.
ClusterSecretStoreThe same, but cluster-wide.Every namespace may reference it, so it is one shared gateway with one set of permissions.[5]

target SecretThe result: a normal v1/Secret, owned by the ExternalSecret.Same namespace as the ExternalSecret.

Three fields of an ExternalSecret matter most today:[6]

  • refreshInterval: how often ESO reads the provider again, such as 1h. With the default refreshPolicy: Periodic, a changed value in AWS reaches the cluster within one interval. 0 means "fetch once, never update".
  • target: the name of the Secret to create. With the default creationPolicy: Owner, ESO sets itself as the owner: delete the ExternalSecret and the Secret goes with it.
  • data[].remoteRef: key is the secret's name in AWS, property picks one JSON key out of its value.

API version. Use external-secrets.io/v1. In the chart installed today (2.13.0), v1 is the only served version of ExternalSecret, SecretStore and ClusterSecretStore; the old v1beta1 is marked deprecated and no longer served. Blog posts with v1beta1 are out of date.

Industry practice. Prefer a namespaced SecretStore per team. A ClusterSecretStore lets every namespace use the controller's permissions; if you need one, limit it with spec.conditions to named namespaces (examples/external-secrets-aws/99-clustersecretstore.yaml), and give the IAM role only the prefixes it really needs.

How ESO proves who it is to AWS

The ESO controller is the Pod in the bottom half of this picture: it reaches AWS through Pod Identity and IAM, and writes the Kubernetes Secret through its own RBAC permissions. The cluster adds AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE and AWS_CONTAINER_CREDENTIALS_FULL_URI (http://169.254.170.23/v1/credentials) to the Pod; the SDK uses them to fetch credentials from the agent.[7] The kube-apiserver token is a separate one, with a different audience.[15]

ESO calls the Secrets Manager API, so it needs AWS credentials. There are three common ways to give them:

On our cluster, infra/eso.tf creates an IAM role whose trust policy allows pods.eks.amazonaws.com to call sts:AssumeRole and sts:TagSession,[11] a policy that allows only secretsmanager:GetSecretValue and secretsmanager:DescribeSecret on codecool/*, and the association from the ServiceAccount external-secrets/external-secrets to that role. With Pod Identity, the SecretStore needs no auth block at all: the controller simply uses the credentials its own Pod was given.[9]

infra/eso.tf (the permission part)
data "aws_iam_policy_document" "eso_read_secrets" {
  statement {
    sid    = "ReadCodecoolSecrets"
    effect = "Allow"
    actions = [
      "secretsmanager:GetSecretValue",
      "secretsmanager:DescribeSecret",
    ]
    resources = [
      "arn:aws:secretsmanager:${var.region}:${data.aws_caller_identity.current.account_id}:secret:${var.secret_name_prefix}*",
    ]
  }
}

resource "aws_eks_pod_identity_association" "eso" {
  cluster_name    = module.eks.cluster_name
  namespace       = var.eso_namespace       # "external-secrets"
  service_account = var.eso_service_account # "external-secrets"
  role_arn        = aws_iam_role.eso.arn
}

Least privilege. No secretsmanager:*, no "Resource": "*". ESO can read secrets whose names start with codecool/ and nothing else: not write them, not list them, not read the production database password that lives under another prefix.

Create the secret in AWS

  1. Store a JSON key/value secret. The value is read from a file, so it does not end up in your shell history.[3]

SecretStore → ExternalSecret → Secret

  1. Tell ESO how to reach Secrets Manager from the demo namespace. No credentials in this file:

    examples/external-secrets-aws/01-secretstore.yaml
    apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: aws-secrets-manager
  namespace: demo
spec:
  provider:
    aws:
      service: SecretsManager
      region: eu-central-1

    Cluster-specific: region: eu-central-1 must be the region where you created the secret in step 7 — use yours (find it with aws configure get region).

    kubectl apply -f examples/external-secrets-aws/01-secretstore.yaml
    kubectl get secretstore -n demo
    Expected output 
    secretstore.external-secrets.io/aws-secrets-manager created
NAME                  AGE   STATUS   CAPABILITIES   READY
aws-secrets-manager   6s    Valid    ReadWrite      True

    Valid means ESO found working credentials for this store. ReadWrite describes what the provider type can do, not what our IAM role allows: the role can only read.

  2. Say what to fetch and where to put it:

    examples/external-secrets-aws/02-externalsecret.yaml
    apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: app-db
  namespace: demo
spec:
  refreshInterval: 1m              # re-read AWS every minute (demo value; 1h is common)
  secretStoreRef:
    kind: SecretStore
    name: aws-secrets-manager
  target:
    name: app-db-credentials       # the Kubernetes Secret ESO creates and owns
    creationPolicy: Owner
  data:
    - secretKey: username          # key in the Kubernetes Secret
      remoteRef:
        key: codecool/demo/app-db  # name of the secret in AWS Secrets Manager
        property: username         # JSON key inside the secret value
    - secretKey: password
      remoteRef:
        key: codecool/demo/app-db
        property: password
    kubectl apply -f examples/external-secrets-aws/02-externalsecret.yaml
    kubectl get externalsecret -n demo
    Expected output 
    externalsecret.external-secrets.io/app-db created
NAME     STORETYPE     STORE                 REFRESH INTERVAL   STATUS         READY   LAST SYNC
app-db   SecretStore   aws-secrets-manager   1m                 SecretSynced   True    5s

    SecretSynced / True is the state you want. LAST SYNC counts up, and drops back to a few seconds every minute when ESO reads AWS again.

A Pod reads it

  1. The Pod uses the Secret twice: as an environment variable and as a mounted file. Every 10 seconds it prints both.

    examples/external-secrets-aws/03-pod.yaml (container part)

        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-db-credentials
              key: password
      volumeMounts:
        - name: db

    kubectl logs -n demo app
    Expected output 
    pod/app created
10:16:34 env=S3cr3t-v1 file=S3cr3t-v1

    Nothing ESO-specific: the Pod reads a normal Secret.

Rotate the value in AWS, watch it arrive

  1. Store a new version in Secrets Manager. Nothing is changed in Kubernetes or Git.

    aws secretsmanager put-secret-value --region eu-central-1 \
  --secret-id codecool/demo/app-db \
  --secret-string file://examples/external-secrets-aws/app-db-v2.json

    Cluster-specific: eu-central-1 is the course region, and the ARN in the output carries your own account ID and random suffix — use your region (find it with aws configure get region).

    Expected output 
    {
    "ARN": "arn:aws:secretsmanager:eu-central-1:640629842382:secret:codecool/demo/app-db-xhB6Cm",
    "Name": "codecool/demo/app-db",
    "VersionId": "dd88cc41-b6ce-4010-94e4-18ec7bf25379",
    "VersionStages": [
        "AWSCURRENT"

  2. Follow the Pod's log in one terminal and the ExternalSecret in another:

    kubectl logs -n demo app -f
    kubectl get externalsecret app-db -n demo -w
    Expected output (the Pod log, trimmed) 
    10:16:54 env=S3cr3t-v1 file=S3cr3t-v1
10:17:04 env=S3cr3t-v1 file=S3cr3t-v1
10:17:14 env=S3cr3t-v1 file=S3cr3t-v1
10:17:24 env=S3cr3t-v1 file=S3cr3t-v1
10:17:34 env=S3cr3t-v1 file=S3cr3t-v1
10:17:44 env=S3cr3t-v1 file=S3cr3t-v2

    Read it in two steps. Within one refreshInterval (1 minute), ESO read AWS again and updated the Secret. Then the kubelet updated the mounted file. In our run, put-secret-value ran at 10:16:34 (Pod log clock, UTC) and the file showed S3cr3t-v2 at 10:17:44, about 70 seconds later: up to 1 minute for ESO's refreshInterval, plus the kubelet's sync delay. Kubernetes refreshes Secret volumes, with a delay of up to the kubelet sync period plus its cache delay.[12] The environment variable never changes: it was copied into the process when the container started, so only a restart picks up the new value (kubectl rollout restart for a Deployment).[13] Stop both with Ctrl+C.

    Mounting a Secret with subPath also freezes it: such a mount gets no updates.[12] If your app reads its password once at start-up, rotation needs a restart no matter how it is mounted.

  3. Cannot wait a whole interval? Any change to the ExternalSecret's metadata triggers a sync now. ESO's documented way is a timestamp annotation:[14]

    kubectl annotate externalsecret app-db -n demo force-sync=$(date +%s) --overwrite
    Expected output 
    externalsecret.external-secrets.io/app-db annotated

  4. Try to change the Secret by hand, then delete the ExternalSecret:

    kubectl patch secret app-db-credentials -n demo -p '{"stringData":{"password":"hacked"}}'
    kubectl get secret app-db-credentials -n demo -o jsonpath='{.data.password}' | base64 -d; echo
    kubectl delete externalsecret app-db -n demo
    kubectl get secret -n demo
    Expected output 
    secret/app-db-credentials patched
S3cr3t-v2
externalsecret.external-secrets.io "app-db" deleted from demo namespace
No resources found in demo namespace.

    ESO watches the Secrets it owns: the manual edit was overwritten with the AWS value within seconds. AWS is the source of truth, not the cluster. And because of creationPolicy: Owner, deleting the ExternalSecret deleted the Secret too. The Pod keeps running with the values it already has; a new Pod would fail to start until the Secret is back. Re-apply 02-externalsecret.yaml to restore it.

When it does not sync

kubectl get externalsecret shows you that something is wrong. kubectl describe shows you what: read the Events at the bottom, then the store.

kubectl describe externalsecret app-db -n demo
kubectl describe secretstore aws-secrets-manager -n demo
Event message (trimmed)CauseFix
SecretStore "aws-secrets-manager" is not ready, and on the store: failed to refresh cached credentials, no EC2 IMDS role foundThe controller has no AWS credentials: no Pod Identity association, or ESO started before it existed. The SDK falls back to the node's metadata service, which the node group blocks for Pods.Check steps 4–6; restart the ESO Deployment.
AccessDeniedException: … is not authorized to perform: secretsmanager:GetSecretValue on resource: …Credentials work, but the IAM policy does not cover this secret, e.g. its name is outside codecool/.Rename the secret under the allowed prefix, or extend the policy deliberately.
error processing spec.data[0] (key: codecool/demo/app-dbb), err: Secret does not existNo secret with that name in this region: a typo in remoteRef.key, or the store's region is wrong.Compare with aws secretsmanager describe-secret --secret-id ….
key passwd does not exist in secret codecool/demo/app-dbThe secret exists, but its JSON has no such key: a typo in remoteRef.property.Match the JSON key exactly; it is case-sensitive.
SecretSynced, but the app still uses the old passwordNot an ESO problem: the app reads an environment variable, a subPath mount, or caches the value.Restart the workload after rotation, or read the mounted file on each use.

  ----     ------                 ----              ----          -------
  Warning  InvalidProviderConfig  2s (x3 over 11s)  secret-store  failed to refresh cached credentials, no EC2 IMDS role found, operation error ec2imds: GetMetadata, exceeded maximum number of attempts, 3, ...

Read it from the bottom up: the store has no credentials, so the store is not ready, so the ExternalSecret cannot sync. Always check the store when the ExternalSecret only says "not ready". After a fix, ESO retries with a growing back-off; the force-sync annotation from step 14 retries at once.

Clean up

kubectl delete -f examples/external-secrets-aws/03-pod.yaml -f examples/external-secrets-aws/02-externalsecret.yaml -f examples/external-secrets-aws/01-secretstore.yaml --ignore-not-found

ESO itself stays installed for the next session; only the demo objects go. The AWS secret is deleted before tofu destroy; see infra/README.md.
