ConfigMap vs Secret

Your win: you can pick ConfigMap or Secret for a setting and say why, predict whether a running app sees a changed value (environment variable, mounted file, or subPath file), and show anyone that a Secret's base64 is not encryption, by decoding one in a single command.

Before this: kubectl basics (Pod, Deployment, get, describe, logs). The instructor runs every command on the shared EKS cluster, in the namespace demo. Watch first; the page is yours to review later. The example files are in examples/configmap-vs-secret/.

Two objects, one job: get settings into a Pod

An image should run unchanged in dev, test and production. What changes between them (a log level, a database host, a password) is kept outside the image, in the cluster, and handed to the Pod at start. Kubernetes has two objects for that, and they work almost the same way:

ConfigMapSecret
Fornon-confidential key-value data[1]a small amount of sensitive data: a password, a token, a key[2]
ExampleLOG_LEVEL=info, an nginx config filethe database password, a TLS private key
Values in the APIplain textbase64-encoded under data (you may write plain text under stringData; it is merged into data)
Max size1 MiB[1]1 MiB[3]
Typed?noyes: Opaque, kubernetes.io/tls, … (below)
Extra care by Kubernetesnonesent only to nodes that run a Pod needing it; mounted on tmpfs (memory), never written to the node's disk[4]

The rule: if leaking the value would hurt, it goes into a Secret. Everything else goes into a ConfigMap. A ConfigMap "does not provide secrecy or encryption".[1] As you will see in a minute, a Secret on its own does not provide much more. What it gives you is a separate object that can be locked down separately.

The industry rule behind it: the Twelve-Factor App

The Twelve-Factor App is a widely used checklist for building apps that run well on cloud platforms. Three of its twelve factors are exactly what ConfigMaps and Secrets are for:

FactorWhat it saysIn Kubernetes
III. ConfigConfig is "everything that is likely to vary between deploys (staging, production, developer environments, etc)", and it needs "strict separation of config from code".[16]One image for every environment. The settings come from a ConfigMap and a Secret per environment, never baked into the image.
IV. Backing servicesA database or queue is an attached resource, "accessed via a URL or other locator/credentials stored in the config". To swap it, "only the resource handle in the config needs to change".[17]The database host goes into the ConfigMap, the username and password into the Secret (db-credentials in the demo below).
V. Build, release, runA release is the build combined with the deploy's config. "Releases are an append-only ledger": "any change must create a new release."[18]Immutable, versioned ConfigMaps (app-config-v1 → -v2) plus a rolling update: a config change is a new release you can roll back.

The litmus test: could you make your repository public right now "without compromising any credentials"?[16] If not, a secret is in your code. Twelve-factor recommends environment variables for config; Kubernetes gives you env vars or files. The principle that matters is the separation, not the delivery mechanism.

Environment variable or file?

A Pod consumes either object in two main ways: as environment variables (env[].valueFrom picks one key, envFrom takes them all) or as files in a volume, one file per key.[1] The difference shows up when you change the value while the Pod runs:

Consumed asRunning Pod sees the change?
Environment variableNo. Env vars are set once, when the container starts. You need a Pod restart.[5]
Volume (whole ConfigMap/Secret as a folder)Yes, eventually. The kubelet swaps the files in place. The delay can be as long as the kubelet sync period plus its cache delay; on our EKS cluster, about 80 seconds.[6]
Volume with subPath (one file placed into an existing folder)No, never. A subPath mount does not receive updates.[6]

The file refreshes, but your app must re-read it. A program that reads its config once at start-up still needs a restart. That is why teams often just roll the Deployment after a change: kubectl rollout restart.

base64 is not encryption

The values under a Secret's data are base64 strings. Base64 is an encoding, like writing a word in Morse code: anyone can turn it back, no key needed. The Kubernetes docs say it plainly: "Base64 encoding is not an encryption method, it provides no additional confidentiality over plain text."[7] It exists so that binary data (a key file, a certificate) fits into YAML and JSON.

By default, Secrets are stored unencrypted in etcd, the cluster's database. Anyone with API access to a Secret can read it, and so can anyone who can create a Pod in that namespace: the Pod can simply mount the Secret.[2]

Secret types

The type field tells Kubernetes and tools what shape the data has. For built-in types the API server checks that the required keys are there.[8] The three you meet most:

TypeHoldsCreate with
Opaqueanything; the default when no type is givenkubectl create secret generic
kubernetes.io/dockerconfigjsonregistry credentials, one key .dockerconfigjson; used in a Pod's imagePullSecrets to pull private imageskubectl create secret docker-registry
kubernetes.io/tlsa certificate and its private key, keys tls.crt and tls.key; typical for Ingress TLSkubectl create secret tls

Others exist: kubernetes.io/dockercfg (legacy format), kubernetes.io/basic-auth, kubernetes.io/ssh-auth, kubernetes.io/service-account-token, and bootstrap tokens.[8]

Immutable: freeze it

Set immutable: true on a ConfigMap or Secret and its data can never change again. You cannot undo this either: the only way out is to delete and recreate it. Two benefits: nobody can break running apps with an accidental edit, and the kubelet stops watching the object, which takes load off the API server in big clusters.[9] A common pattern is a versioned name (app-config-v1, app-config-v2): to change config, create a new object and point the Deployment at it. That gives a normal rolling update, and a rollback.

Keeping Secrets secret: the industry baseline

Kubernetes' own docs list the minimum steps for using Secrets safely.[2][7] On our EKS cluster:

1. Encryption at rest

The API server can encrypt objects before writing them to etcd; without that, it stores "plain-text representations".[10] On EKS 1.28 and later this is on by default: envelope encryption of all Kubernetes API data with AWS KMS. Each object is encrypted with a data encryption key (DEK); the DEK itself is encrypted with a key encryption key (KEK) that never leaves AWS KMS. The KEK is an AWS owned key by default, or your own customer managed key (CMK), which shows up in CloudTrail and can be rotated and audited.[11]

Encryption at rest protects the disk and backups of etcd. It does nothing against someone who may get the Secret through the API: the API server decrypts before it answers. That is what RBAC is for.

2. RBAC with least privilege

Give humans and workloads only the Secret access they need. Watch out for list and watch: granting list on Secrets lets the subject read all Secret data in the namespace, not just names.[12] If a workload needs one Secret, grant get on that one, by name (resourceNames).[13] And remember: whoever can create Pods in a namespace can read its Secrets. Lesson 02 is all about this.

3. Never commit Secrets to Git

A Secret manifest with base64 values, checked into a repository, is readable by everyone who can read the repository, forever (Git keeps history).[7] So how do production teams put Secrets into a GitOps workflow? The value lives in a secret store (AWS Secrets Manager), and only a reference to it is committed. Lesson 03 builds exactly that with the External Secrets Operator.

4. Keep them small, and keep them out of logs

Each ConfigMap or Secret is limited to 1 MiB, to protect the memory of the API server and kubelets; big files belong in a volume or object storage.[3] Inside the app, the secret must stay secret: never log it, never send it anywhere untrusted. Mount a Secret only into the containers that need it.[7]

Demo

Create the ConfigMap and the Secret

  1. The namespace and the ConfigMap. One key is a single value, the other a whole file:

    examples/configmap-vs-secret/01-configmap.yaml
    apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: demo
data:
  LOG_LEVEL: "info"                 # a single value, used as an environment variable
  greeting.txt: |                   # a whole file, used as a mounted volume
    Hello from the ConfigMap, version 1
    kubectl apply -f examples/configmap-vs-secret/00-namespace.yaml -f examples/configmap-vs-secret/01-configmap.yaml
    Expected output 
    namespace/demo created
configmap/app-config created

  2. The Secret. It is not in a YAML file in the repo, on purpose (best practice 3): create it from the command line. Single quotes stop the shell from interpreting !.[14]

    kubectl create secret generic db-credentials -n demo --from-literal=username=app --from-literal=password='S3cr3t!'
    kubectl get configmap,secret -n demo
    Expected output 
    secret/db-credentials created
NAME                         DATA   AGE
configmap/app-config         2      1s
configmap/kube-root-ca.crt   1      1s

NAME                    TYPE     DATA   AGE
secret/db-credentials   Opaque   2      1s

    generic made an Opaque Secret with two keys. kube-root-ca.crt is put in every namespace automatically; ignore it.

    The literal password is now in your shell history. Fine for a demo; in real work read it from a file (--from-file) or, better, let a tool sync it from a secret store (lesson 03).

Decode it: base64 is not encryption

  1. kubectl get secret db-credentials -n demo -o yaml
    Expected output (your uid and versions differ) 
    apiVersion: v1
data:
  password: UzNjcjN0IQ==
  username: YXBw
kind: Secret
metadata:
  creationTimestamp: "2026-10-22T10:11:06Z"
  name: db-credentials
  namespace: demo
  resourceVersion: "1961"
  uid: 78c12271-755f-4188-9703-a189d14b1023
type: Opaque

    Looks scrambled. It is not. One pipe turns it back:

    kubectl get secret db-credentials -n demo -o jsonpath='{.data.password}' | base64 -d
    Expected output 
    S3cr3t!

    No key, no password, no special access beyond get on the Secret. And the other way: echo -n 'S3cr3t!' | base64 prints UzNjcjN0IQ==, the exact string from the YAML. Anyone who sees a Secret manifest sees the password.

    kubectl describe secret is the polite view: it prints only sizes (password: 7 bytes). Use it when someone is looking over your shoulder.

The demo app reads both

  1. The app is a tiny shell loop. Every 5 seconds it prints what it sees three ways: from environment variables, from the mounted folders, and from one file mounted with subPath. The important part of the manifest:

    examples/configmap-vs-secret/02-app.yaml (excerpt)
              env:
            - name: LOG_LEVEL               # one key from the ConfigMap
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: LOG_LEVEL
            - name: DB_PASSWORD             # one key from the Secret
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
          volumeMounts:
            - name: config                  # the whole ConfigMap as a folder
              mountPath: /etc/config
              readOnly: true
            - name: secret                  # the whole Secret as a folder
              mountPath: /etc/secret
              readOnly: true
            - name: config                  # ONE file via subPath: never refreshed
              mountPath: /app/greeting.txt
              subPath: greeting.txt
              readOnly: true
      volumes:
        - name: config
          configMap:
            name: app-config
        - name: secret
          secret:
            secretName: db-credentials
    kubectl apply -f examples/configmap-vs-secret/02-app.yaml
    kubectl rollout status deployment/demo-app -n demo
    kubectl logs deployment/demo-app -n demo --tail=3
    Expected output 
    deployment.apps/demo-app created
Waiting for deployment "demo-app" rollout to finish: 0 of 1 updated replicas are available...
deployment "demo-app" successfully rolled out
env:     LOG_LEVEL=info DB_PASSWORD=S3cr3t!
volume:  greeting=Hello from the ConfigMap, version 1 password=S3cr3t!
subPath: greeting=Hello from the ConfigMap, version 1
    This app prints the password only so you can watch it change. A real app must never log a Secret.[7]

  2. Look at a mounted folder. Each key is a file; the files are symlinks into a hidden, timestamped folder:

    kubectl exec deployment/demo-app -n demo -- ls -la /etc/secret
    Expected output 
    total 0
drwxrwxrwt    3 root     root           120 Oct 22 10:11 .
drwxr-xr-x    1 root     root            82 Oct 22 10:11 ..
drwxr-xr-x    2 root     root            80 Oct 22 10:11 ..2026_10_22_10_11_10.3052162131
lrwxrwxrwx    1 root     root            32 Oct 22 10:11 ..data -> ..2026_10_22_10_11_10.3052162131
lrwxrwxrwx    1 root     root            15 Oct 22 10:11 password -> ..data/password
lrwxrwxrwx    1 root     root            15 Oct 22 10:11 username -> ..data/username

    That symlink is the trick behind live updates: on a change, the kubelet writes a new timestamped folder and flips ..data to point at it, in one step. A subPath mount bypasses the symlink and pins the file that existed at start, which is why it never updates.

Change the values while the app runs

  1. Change both objects. stringData lets you write the Secret in plain text; the API server encodes it into data.[15]

    kubectl patch configmap app-config -n demo --type merge -p '{"data":{"LOG_LEVEL":"debug","greeting.txt":"Hello from the ConfigMap, version 2\n"}}'
    kubectl patch secret db-credentials -n demo --type merge -p '{"stringData":{"password":"N3wP4ss!"}}'
    Expected output 
    configmap/app-config patched
secret/db-credentials patched

    Predict before you look: which of the three lines will change?

  2. Wait about 1–2 minutes, then:

    kubectl logs deployment/demo-app -n demo --tail=3
    Expected output (here it took about 80 seconds) 
    env:     LOG_LEVEL=info DB_PASSWORD=S3cr3t!
volume:  greeting=Hello from the ConfigMap, version 2 password=N3wP4ss!
subPath: greeting=Hello from the ConfigMap, version 1

    Only the volume: line moved. Same Pod, no restart: the kubelet swapped the files. The environment variables still hold the values from container start, and the subPath file is stuck on version 1. Both will stay like that for the life of the container.

    How long the volume: line takes depends on the kubelet sync period plus its cache delay: up to about 1–2 minutes. On our EKS cluster it took 80 seconds. If it has not changed yet, wait and run the command again.

  3. Restart the Pods to pick everything up:

    kubectl rollout restart deployment/demo-app -n demo
    kubectl rollout status deployment/demo-app -n demo
    kubectl logs deployment/demo-app -n demo --tail=3
    Expected output 
    deployment.apps/demo-app restarted
Waiting for deployment "demo-app" rollout to finish: 1 old replicas are pending termination...
deployment "demo-app" successfully rolled out
env:     LOG_LEVEL=debug DB_PASSWORD=N3wP4ss!
volume:  greeting=Hello from the ConfigMap, version 2 password=N3wP4ss!
subPath: greeting=Hello from the ConfigMap, version 2

    New container, new environment: all three lines agree.

    Right after a restart, kubectl logs deployment/demo-app may print Found 2 pods, using pod/… and show the old Pod, with the old values. Wait a few seconds until the old Pod is gone, then run it again.

Secret types, immutability, size limit

  1. Create a registry Secret and a TLS Secret. The TLS Secret needs a certificate; a throwaway self-signed one will do:

    openssl req -x509 -newkey rsa:2048 -nodes -days 30 -subj "/CN=demo.example.com" -keyout tls.key -out tls.crt 2>/dev/null
    Expected output 
    (nothing printed; tls.key and tls.crt now exist in the current folder)
    kubectl create secret docker-registry regcred -n demo --docker-server=registry.example.com --docker-username=ci-bot --docker-password=not-a-real-token
    kubectl create secret tls demo-tls -n demo --cert=tls.crt --key=tls.key
    kubectl get secrets -n demo
    Expected output 
    secret/regcred created
secret/demo-tls created
NAME             TYPE                             DATA   AGE
db-credentials   Opaque                           2      102s
demo-tls         kubernetes.io/tls                2      0s
regcred          kubernetes.io/dockerconfigjson   1      1s

    The TYPE column tells you what each one is for. And the registry token is no safer than the password was:

    kubectl get secret regcred -n demo -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d
    Expected output 
    {"auths":{"registry.example.com":{"username":"ci-bot","password":"not-a-real-token","auth":"Y2ktYm90Om5vdC1hLXJlYWwtdG9rZW4="}}}

    The dot in the key name .dockerconfigjson must be escaped as \. in jsonpath. The inner auth field is base64 again (of ci-bot:not-a-real-token): obscured, not secret.

  2. An immutable ConfigMap, and an attempt to change it:

    examples/configmap-vs-secret/03-immutable-configmap.yaml
    apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v1
  namespace: demo
data:
  LOG_LEVEL: "info"
immutable: true
    kubectl apply -f examples/configmap-vs-secret/03-immutable-configmap.yaml
    kubectl patch configmap app-config-v1 -n demo --type merge -p '{"data":{"LOG_LEVEL":"debug"}}'
    Expected output 
    configmap/app-config-v1 created
The ConfigMap "app-config-v1" is invalid: data: Forbidden: field is immutable when `immutable` is set

    Refused by the API server. To change it: create app-config-v2 and point the Deployment at it.

  3. The size limit. Try to store a file just over 1 MiB:

    head -c 1100000 /dev/zero | tr '\0' 'x' > big.txt
    kubectl create configmap too-big -n demo --from-file=big.txt
    Expected output 
    error: failed to create configmap: ConfigMap "too-big" is invalid: []: Too long: may not be more than 1048576 bytes

    1048576 bytes is exactly 1 MiB. Secrets have the same limit.

Who can read it, and where is it encrypted?

  1. Ask the API whether the namespace's default ServiceAccount, which every Pod runs as unless told otherwise, may read Secrets:

    kubectl auth can-i get secrets -n demo --as system:serviceaccount:demo:default
    kubectl auth can-i list secrets -n demo
    Expected output 
    no
yes

    The Pod's identity gets nothing by default. Good. You, the cluster admin, may list, which means you can read every Secret in the namespace. Lesson 02 shows how to grant exactly what is needed, and no more.

  2. Check how our EKS cluster encrypts Kubernetes data at rest:

    aws eks describe-cluster --region eu-central-1 --name codecool-demo --query cluster.encryptionConfig

    Cluster-specific: codecool-demo and eu-central-1 are our cluster's name and region, and the key ARN in the output contains our account ID — use yours (find them with aws eks list-clusters --region <your-region>).

    Expected output (our cluster has a customer managed KMS key) 
    [
    {
        "resources": [
            "secrets"
        ],
        "provider": {
            "keyArn": "arn:aws:kms:eu-central-1:640629842382:key/d8075eea-3451-4157-80bc-c0e560e04a30"
        }
    }
]

    Our cluster uses a customer managed key: the terraform-aws-modules/eks module that built it creates one by default. So you see its ARN. "resources": ["secrets"] is kept for backward compatibility only: since 1.28, EKS envelope-encrypts all API data, ConfigMaps included. With the default AWS owned key, no key ARN is shown; the EKS console lists the encryption instead.[11]

    If you bring your own KMS key and it is later disabled or deleted, the cluster cannot decrypt its own data. A deleted key leaves the cluster unrecoverable.[11] Guard the key's IAM permissions accordingly.

  3. Clean up what lesson 02 does not need. Keep the namespace and app-config.

    kubectl delete deployment demo-app -n demo
    kubectl delete secret db-credentials regcred demo-tls -n demo
    kubectl delete configmap app-config-v1 -n demo
    rm tls.key tls.crt big.txt
    Expected output 
    deployment.apps "demo-app" deleted from demo namespace
secret "db-credentials" deleted from demo namespace
secret "regcred" deleted from demo namespace
secret "demo-tls" deleted from demo namespace
configmap "app-config-v1" deleted from demo namespace

    rm prints nothing. It removes the throwaway certificate, key and test file from your folder.
