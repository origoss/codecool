Anatomy of a Kubernetes YAML: fields, labels and selectors

Your win: you can read any Kubernetes manifest and name its four parts, and you can explain how a Deployment and a Service find their Pods, and why a one-letter typo in a label breaks traffic without any error.

Before this: you know kubectl get, describe and apply, and what a Pod, a Deployment and a Service are. Every later lesson (ConfigMap, RBAC, ExternalSecret, NetworkPolicy) is written in this format.

Four parts, every time

Every object you send to Kubernetes has the same skeleton. These fields are required:[1]

apiVersion: apps/v1          # (1) which API (group/version) handles this object
kind: Deployment             # (2) what type of object
metadata:                    # (3) identity
  name: demo-app             #     unique per kind + namespace
  namespace: demo            #     omit it and you get "default"
  labels:                    #     key/value tags: selectors match on these
    app: demo-app
  annotations:               #     free-form notes for tools, never used for selecting
    owner: platform-team
spec:                        # (4) desired state: what YOU want
  replicas: 2
  selector:
    matchLabels:
      app: demo-app          #     must match the template labels below
  template:                  #     a Pod, nested: it has its own metadata + spec
    metadata:
      labels:
        app: demo-app
        tier: web
    spec:
      containers:
      - name: app            # "- " starts a list item
        image: traefik/whoami:v1.12.0
        env:
        - name: WHOAMI_PORT_NUMBER
          value: "8080"       #     (the full file also sets runAsNonRoot)
---                          # separates objects in one file
apiVersion: v1               # core group: just "v1"
kind: ConfigMap
metadata:
  name: app-config
  namespace: demo
data:                        # ConfigMap and Secret: data instead of spec
  LOG_LEVEL: "info"          # values must be strings: quote numbers ("3")

YAML rules that bite

  • Indent with spaces only, never tabs. The indent decides what belongs to what.
  • key: value is a map; - item is a list item.
  • yes, no, 3, 1.10 are read as booleans or numbers. Quote them when they must be strings.
  • | keeps a multi-line block with its line breaks: good for a whole config file inside a ConfigMap.

Don't guess field names: look them up. kubectl explain prints the schema of any field, straight from your cluster:

Labels and selectors: how objects find each other

Kubernetes objects do not hold direct links to each other, like a list of Pod names. They find each other with labels (key/value tags) and selectors (queries over labels). "The label selector is the core grouping primitive in Kubernetes." Labels "do not provide uniqueness": many objects are expected to carry the same label.[3]

Why it is built this way: Pods come and go. Every restart, rollout or scale-up makes new Pods with new names and new IPs, so a fixed list of Pods would be out of date within minutes. A selector is a standing query: whatever Pods carry app=demo-app right now are the members.

Deployment ──selector app=demo-app──▶ ReplicaSet ──▶ Pods (labels: app=demo-app)
                                                       ▲
Service ──────selector app=demo-app────────────────────┤  → EndpointSlice (Pod IPs)
NetworkPolicy ──podSelector app=demo-app───────────────┘  (lesson 04)
ObjectFieldWhat the selector decides
Deployment / ReplicaSetspec.selector.matchLabels (+ matchExpressions)which Pods it counts and manages[4]
Servicespec.selector (a plain map)which Pods get traffic: the Service controller "continuously scans for Pods that match its selector" and updates the EndpointSlices[5]
NetworkPolicypodSelector, namespaceSelectorwhich Pods a rule applies to (lesson 04)
Youkubectl get pods -l app=demo-appfiltering

Several requirements are joined with AND: the comma means &&, and "there is no logical OR operator".[3] All requirements from matchLabels and matchExpressions must be satisfied.[4]

Demo

The selector must match the template

  1. 03-deployment-bad-labels.yaml is the same file with one typo in the Pod template: app: demo-ap.

    kubectl apply -f examples/yaml-anatomy/00-namespace.yaml
kubectl apply -f examples/yaml-anatomy/03-deployment-bad-labels.yaml
    Expected output 
    namespace/demo created
configmap/app-config created
The Deployment "demo-app" is invalid: spec.template.metadata.labels: Invalid value: {"app":"demo-ap","tier":"web"}: `selector` does not match template `labels`

    The API rejects it: a Deployment whose selector cannot find its own Pods would create Pods forever. ".spec.selector must match .spec.template.metadata.labels, or it will be rejected by the API."[4]

    Look closely: the ConfigMap in the same file was created. kubectl apply sends each object on its own; a file is not all-or-nothing.

A Deployment's selector is frozen

  1. kubectl patch deployment demo-app -n demo --type=merge -p '{"spec":{"selector":{"matchLabels":{"app":"other"}},"template":{"metadata":{"labels":{"app":"other"}}}}}'
    Expected output 
    The Deployment "demo-app" is invalid: spec.selector: Invalid value: {"matchLabels":{"app":"other"}}: field is immutable

    ".spec.selector is immutable after creation of the Deployment in apps/v1."[4] To change it you delete and recreate the Deployment, so choose it carefully on day one.

  2. Clean up:

    kubectl delete namespace demo
    Expected output 
    namespace "demo" deleted

Best practices

Never let selectors overlap. Do not create other Pods or controllers whose labels match a Deployment's selector: "the first Deployment thinks that it created these other Pods. Kubernetes does not stop you from doing this." With overlapping selectors, "the controllers will fight with each other and won't behave correctly."[4]
  • Use the recommended labels, with the shared prefix app.kubernetes.io: name, instance, version, component, part-of, managed-by. They let tools understand your objects "in a common manner".[6]
  • Keep the selector small and stable, for example app.kubernetes.io/name + app.kubernetes.io/instance. Put values that change, like version, in extra labels and never in the selector: the selector is immutable.
  • Labels are for selecting; annotations are for everything else (owner, Git commit, tool settings). "Non-identifying information should be recorded using annotations."[3]
  • Debug from the selector: kubectl describe svc shows Selector and Endpoints; compare them with kubectl get pods --show-labels.
