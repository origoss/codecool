NetworkPolicy: deny everything, then allow one path

Your win: you can write a default-deny NetworkPolicy for a namespace plus one allow rule, explain why the first curl after it fails on DNS rather than on the backend, and predict which curl succeeds and which one times out.

Before this: you know Pods, Deployments, Services and labels (the Pod-to-Pod basics), and the demo namespace from lesson 01. The instructor runs the demo on the shared EKS cluster from the course folder; the files are in examples/network-policies/. Keep the reference sheet open.

By default, every Pod can reach every Pod

Kubernetes networking is flat: any Pod can open a connection to any other Pod, in any namespace, and to the outside world. Nothing is filtered until you say so.[2] In Kubernetes words, a Pod is non-isolated for ingress (incoming) and for egress (outgoing) traffic: all connections are allowed.[1]

That is convenient on day one and dangerous on day two hundred: one compromised Pod can scan and reach your database, your internal admin APIs, and the cloud metadata endpoint. A NetworkPolicy is a namespaced object that controls traffic at the IP address and port level, OSI layer 3 and 4.[1]

No enforcing CNI, no effect

The API server stores a NetworkPolicy like any other object, but it does not filter a single packet. The network plugin (CNI) does that. In the docs' own words: "Creating a NetworkPolicy resource without a controller that implements it will have no effect."[1] No error, no warning: the policy just sits there.

WhereWho enforces NetworkPolicy
EKS (our cluster)Amazon VPC CNI, with network policy turned on: add-on setting "enableNetworkPolicy": "true". A second container, the network policy agent, then runs in every aws-node Pod and enforces rules with eBPF.[3] Linux EC2 nodes only: not Fargate, not Windows.[2]
ElsewhereA CNI that implements it, typically Calico[4] or Cilium.[5] Both also have their own richer policy types; this lesson uses only the standard one.
Learn Calico properly: Calico is a network plugin that enforces Kubernetes NetworkPolicy, and adds its own richer policy types.[4] Tigera, the company behind it, offers a free course (Tigera Academy, CCO-L1) on Kubernetes networking and network policy with Calico.[12] It is the recommended next step after this lesson.

Anatomy: whom it applies to, whom it lets in

A policy has two halves. spec.podSelector picks the Pods the policy applies to, in its own namespace; {} means all of them. The rules then list who may talk to those Pods (ingress → from) and whom they may talk to (egress → to), optionally with ports.[1]

policyTypes says which directions the policy isolates. If you leave it out, Ingress is always set and Egress only when the policy has egress rules.[1] Write it out every time: it makes intent readable.

Inside from and to you pick peers with four kinds of selector:[1]

SelectorSelects
podSelectorPods with these labels, in the same namespace as the policy.
namespaceSelectorAll Pods in namespaces with these labels. Every namespace has the automatic label kubernetes.io/metadata.name: <name>, so you can select one by name.[6]
both, in one entryPods with these labels, inside namespaces with those labels (AND).
ipBlockA CIDR range. Meant for addresses outside the cluster, because Pod IPs change.

Policies only ever add allows

There is no "deny" rule in a NetworkPolicy. As soon as any policy selects a Pod for a direction, that Pod is isolated in that direction, and what is allowed is the union of all rules of all policies that select it. Policies never conflict and their order does not matter.[1]

And a connection needs both ends: the egress side of the source Pod and the ingress side of the destination Pod must both allow it.[1] So "deny everything, then allow frontend → backend" takes two allow rules, one on each side.

Within one rule, peers and ports go together. A rule "from app=frontend, port 8080" plus another rule "from app=metrics, port 9090" does not let the frontend in on 9090.

The YAML trap: one dash turns AND into OR

These two snippets differ by one character. The docs warn: "Be careful to use correct YAML syntax."[1]

AND: one list item, both selectors (what you usually want)
egress:
  - to:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: kube-system
        podSelector:
          matchLabels:
            k8s-app: kube-dns
OR: two list items (note the second "-")
egress:
  - to:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: kube-system
      - podSelector:
          matchLabels:
            k8s-app: kube-dns

The first allows "CoreDNS Pods in kube-system". The second allows "any Pod in kube-system" or "Pods labelled k8s-app=kube-dns in this namespace". Both are valid YAML, both are accepted. When in doubt, kubectl describe shows how Kubernetes read it: one To: block means AND, two mean OR (step 7 below).[1]

Do it

Two apps in demo: backend (nginx on port 8080, behind a Service named backend) and frontend (a Pod with curl). Every curl uses -m 3: a blocked packet is dropped, not refused, so without a timeout you would just wait.

  1. Deploy both apps. They are Deployments, not bare Pods, on purpose: on EKS, enforcement is reliable only for Pods that have an owner such as a Deployment.[2] The Service port equals the container port (8080), which the VPC CNI also requires.

  template:
    metadata:
      labels:
        app: backend
    ...
kind: Service          # backend:8080 -> Pods with app=backend
  ports:
    - port: 8080
      targetPort: 8080
...
kind: Deployment       # frontend
  template:
    metadata:
      labels:
        app: frontend
    kubectl apply -f examples/network-policies/00-namespace.yaml -f examples/network-policies/01-apps.yaml
    kubectl -n demo get pods -l 'app in (frontend,backend)'

    Why sleep 5 in the test Pod? By default the VPC CNI starts a new Pod with allow-all and applies its policies a moment later ("standard mode").[3] A test that fires in the first second can pass when it should fail.

  3. Deny everything, both directions, for every Pod in demo. The policy has no rules at all, so nothing is allowed.[1]

    examples/network-policies/02-default-deny.yaml
    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: demo
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
    kubectl apply -f examples/network-policies/02-default-deny.yaml
    kubectl -n demo exec deploy/frontend -- curl -sS -m 3 -o /dev/null -w '%{http_code}\n' http://backend:8080
    Expected output 
    networkpolicy.networking.k8s.io/default-deny-all created
000
curl: (28) Resolving timed out after 3001 milliseconds
command terminated with exit code 28

    Read the error closely: curl never got to the backend. It could not even resolve the name backend.

  4. Allow frontend → backend on TCP 8080, on both ends: ingress on the backend, egress on the frontend.

    examples/network-policies/03-allow-frontend-to-backend.yaml
    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-from-frontend
  namespace: demo
spec:
  podSelector:
    matchLabels:
      app: backend          # applies TO the backend Pods
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend # only from frontend Pods in this namespace
      ports:
        - protocol: TCP
          port: 8080
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frontend-allow-to-backend
  namespace: demo
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes:
    - Egress
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: backend
      ports:
        - protocol: TCP
          port: 8080
    kubectl apply -f examples/network-policies/03-allow-frontend-to-backend.yaml
    kubectl -n demo exec deploy/frontend -- curl -sS -m 3 -o /dev/null -w '%{http_code}\n' http://backend:8080
    kubectl -n demo get svc backend -o jsonpath='{.spec.clusterIP}{"\n"}'
    kubectl -n demo exec deploy/frontend -- curl -sS -m 3 -o /dev/null -w '%{http_code}\n' http://172.20.155.41:8080

    Cluster-specific: 172.20.155.41 is the ClusterIP of the backend Service on our cluster — use yours (find it with the jsonpath command just above).

    Expected output (use your own ClusterIP) 
    networkpolicy.networking.k8s.io/backend-allow-from-frontend created

    By IP it works; by name it does not. The allow rule is right. DNS is blocked: name lookups go to CoreDNS in kube-system on port 53, and default-deny egress blocked that too.[1] This is the classic outage after someone "just adds a default deny".

  5. Allow DNS egress for every Pod in demo, to the CoreDNS Pods only. The CoreDNS Service is still called kube-dns and its Pods carry k8s-app=kube-dns, for backward compatibility.[7] DNS uses UDP and TCP 53.

    examples/network-policies/04-allow-dns.yaml
    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: demo
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:          # no "-" here: same item, so AND
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
    kubectl apply -f examples/network-policies/04-allow-dns.yaml
    kubectl -n demo exec deploy/frontend -- curl -sS -m 3 -o /dev/null -w '%{http_code}\n' http://backend:8080
    Expected output 
    networkpolicy.networking.k8s.io/allow-dns-egress created
200

  6. After: test from the outside with an ephemeral Pod. Without the app=frontend label it is just another Pod in demo: DNS works now, but the connection itself is dropped. Then give it the frontend label and it gets in.[8]

Two recipes from the community cookbook

Kubernetes Network Policy Recipes is a widely used collection of ready-made policies, each with a use case, the YAML and a way to try it.[9] Before you write a policy from scratch, look there. Two recipes that go beyond today's demo:

Recipe 04: deny all traffic from other namespaces

Use case: Pods in test must never reach the database in prod; or each customer has a namespace, and namespaces must not talk to each other.[10]

kind: NetworkPolicy
apiVersion: networking.k8s.io/v1
metadata:
  namespace: demo
  name: deny-from-other-namespaces
spec:
  podSelector: {}          # applies to ALL Pods in demo
  ingress:
  - from:
    - podSelector: {}      # from ALL Pods, and with no namespaceSelector: only this namespace

File: 06-recipe-deny-from-other-namespaces.yaml (the recipe uses namespace default; here demo).

kubectl create namespace foo
kubectl run web -n demo --image=nginx:1.27-alpine --labels=app=web --expose --port=80
kubectl apply -f examples/network-policies/06-recipe-deny-from-other-namespaces.yaml
kubectl run test -n foo --rm -i --restart=Never --image=curlimages/curl:8.11.1 --command -- sh -c 'sleep 5; curl -sS -m 3 -o /dev/null -w "%{http_code}\n" http://web.demo'
kubectl run test -n demo --rm -i --restart=Never --image=curlimages/curl:8.11.1 --command -- sh -c 'sleep 5; curl -sS -m 3 -o /dev/null -w "%{http_code}\n" http://web.demo'
Expected output (the two test runs) 
# from namespace foo: blocked
curl: (28) Connection timed out after 3002 milliseconds
000
# from namespace demo: allowed
200

sleep 5 waits out the short window in which a brand-new Pod is not yet isolated (see the sleep 5 note in the demo above).

The key is a podSelector without a namespaceSelector: it only ever matches Pods in the policy's own namespace.[1]

Recipe 14: deny external egress, and a trap in it

Use case: an app may talk to the cluster but must never open connections to the internet (data exfiltration, unexpected downloads).[11] The recipe as published allows only DNS to kube-dns:

spec:
  podSelector:
    matchLabels:
      app: foo
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
      - port: 53
        protocol: UDP
      - port: 53
        protocol: TCP

The recipe says the Pod can still reach the in-cluster web Service. We tested it (07-recipe-deny-external-egress.yaml, Pod labelled app=foo):

Actual output with the recipe as published 
web: curl: (28) Connection timed out after 3002 milliseconds
000
example.com: 000
curl: (28) Connection timed out after 3000 milliseconds

Both are blocked. Egress is an allow-list: only what is listed is allowed, and only DNS is listed. To keep in-cluster traffic, add one more rule: namespaceSelector: {} selects every Pod in every namespace, but never an IP outside the cluster (08-recipe-deny-external-egress-fixed.yaml):

  egress:
  - to: ...                 # the DNS rule, unchanged
  - to:
    - namespaceSelector: {}   # any Pod in the cluster
Output with the fix 
web: 200
example.com: curl: (28) Connection timed out after 3001 milliseconds
000

The lesson behind the trap: a recipe from a trusted repository is still only a starting point. Test what must work and what must fail before you ship it.

Industry practice

  • Default deny per namespace, from day one. Ship default-deny-all plus allow-dns-egress with every new namespace, then add one small allow policy per real flow. NetworkPolicy has no cluster-wide default of its own.[1]
  • Label hygiene. Policies select by labels, so labels are now a security control. Use a few stable, meaningful labels (app, tier), never select on pod-template-hash, and review label changes like firewall changes.
  • Test with an ephemeral curl Pod, always with a timeout. Test both what must work and what must not work, using kubectl run --rm with and without the expected labels.
  • Know the limit: L3/L4 only. A NetworkPolicy sees IPs, ports and protocols. It cannot allow "only GET /api", cannot do anything with TLS, and cannot target a Service by name.[1] HTTP-level rules need a service mesh, a gateway or a CNI extension such as Cilium's own policy type.

Before you add a default deny on EKS: it blocks DNS (step 4) and also the EC2 instance metadata service. Pods that use EKS Pod Identity or IRSA, like the External Secrets Operator in lesson 03, do not use IMDS; every other destination a Pod needs (AWS APIs, an external database) needs its own egress allow.[2] Roll out deny policies namespace by namespace and watch for timeouts.

Not every timeout is a NetworkPolicy. On our cluster, the first run of the recipes timed out on port 80 between Pods on different nodes with no policy at all: the EKS node security group only allowed node-to-node ports 1025–65535 (fixed in infra/main.tf, node_security_group_additional_rules, rule ingress_self_all). Check kubectl get networkpolicy -A first; if there is none and it still times out, look at the security groups.
